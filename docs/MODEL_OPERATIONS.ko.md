# 하이·미들·로우 개발 운영

**프로젝트 크레딧:** 강희성(Hee-sung Kang) · 이도원(Do-won Lee) · 박성모(Sungmo Park)

## 초록

작업의 불확실성과 위험에 맞춰 모델 역량을 배분합니다. 프런티어 모델은 구조·인터페이스·난제 해결, 중형 모델은 범위가 정해진 구현, 로컬 모델은 정확한 작업 카드와 실행 가능한 검증이 있는 반복 작업을 맡습니다. 목표는 돈·시간·사람의 검토 노력 대비 수용 가능한 결과를 늘리는 것입니다. 특정 모델의 성능이나 비용 우위를 측정했다는 주장은 아닙니다.

## 역할 배분

하이·미들·로우 비유의 핵심은 자원 배분입니다. 부족한 고성능 자원은 결과를 바꾸는 곳에 사용하고 일상 작업에는 신뢰할 수 있는 지원 체계를 만듭니다.

| 단계 | 적합한 작업 | 넘길 산출물 | 종료 조건 |
|---|---|---|---|
| 하이·프런티어 | 모호한 구조, 핵심 인터페이스, 시스템적 실패, 영향이 큰 검토 | 결정·불변 조건·계약·작은 작업·기준 검사 | 대화 전체를 재구성하지 않고 구현을 이어갈 수 있음 |
| 미들·중형 | 정해진 인터페이스를 쓰는 기능·통합·검증 확대 | 검토 가능한 구현·경계 조건·검사 | 범위와 실패 형태가 후속 반복 작업으로 다룰 만큼 명확함 |
| 로우·로컬 | 작은 수정·명시된 테스트·문서·반복 편집 | 최소 변경·실제 테스트·갱신된 맥락 | 숨은 변경이나 허위 근거 없이 수용 기준 통과 |

개발 모델 배분은 제품 사용자의 모델 선택과 별개입니다. 명시된 모델 고정 방침이 자동 배분보다 우선합니다. SovaRoll의 공개 직후 코딩은 Gemma 4만 사용하며, 혼합 운용 방법론은 다른 프로젝트나 이후 명시적 방침 변경에 적용할 수 있습니다.

## 작업 계약

목표, 허용 파일·진입점, 지켜야 할 동작, 수용 기준, 실제 검증 명령, 복구 범위와 중단 조건을 정합니다. 문서·코드·데이터 이전·공개 중 무엇인지 구분합니다. 코딩 요청이 곧 외부 공개·유료 추론·파괴적 작업의 허가는 아닙니다.

기준 상태에서 시작합니다. 컴파일러나 테스트 출력 폴더가 없는 문제와 음악 결과가 틀린 제품 문제를 구분합니다. 구현·기대값을 바꾸기 전에 첫 실패부터 진단하고 사용자 프로젝트·다른 변경을 보존합니다.

## 실행과 상위 단계 인계

1. 사람이 목표와 허용 모델을 정합니다.
2. Git·지침·`CONTEXT.md`·작업 카드 하나를 읽습니다.
3. 관련 파일을 체크포인트에 저장하고 필요한 기호·코드 일부를 읽습니다.
4. 검토할 수 있는 변경 하나를 만들고 필요한 정상·거부·상태 보존 동작을 검사합니다.
5. 차이와 실제 출력을 검토해 근거와 함께 완료 또는 차단합니다.
6. 영어 `CONTEXT.md`를 갱신한 뒤 인계하거나 종료합니다.

로컬 작업이 반복 실패하면 범위를 줄이고 남은 조건을 정확히 기록합니다. 저장소의 재시도 한도를 따릅니다. SovaRoll은 같은 실패를 세 번 해결하지 못하면 작업 체크포인트로 복구하고 block합니다. 상위 모델 인계가 허용돼 있으면 최소 재현·오류·시도를 전달합니다. 로컬 전용이면 사람에게 결정을 돌리고 프런티어 모델을 몰래 호출하지 않습니다.

## 짧은 컨텍스트 관리

`CONTEXT.md`는 짧은 현재 상태입니다. 목표·지속 결정·모델 방침·작업 ID·관련 경로·관찰한 검사·차단 원인·다음 명령·공개 상태를 넣습니다. 약 80줄을 출발점으로 삼되 실제 토큰을 측정합니다. 줄 수만으로 안전한 컨텍스트 길이를 보증할 수는 없습니다.

완료한 세부 기록은 `docs/context/`, 미래 작업은 작업 큐, 원시 출력은 로그에 둡니다. 매번 전부 읽지 않습니다. 줄이는 과정에서도 미해결 제약은 보존합니다. 현재 기억은 영어 한 파일로 유지하고 한국어 안내는 연결만 합니다.

저장소를 바꾸면 그 저장소의 지침과 맥락을 다시 읽습니다. 이전 작업의 가정·작업 폴더·자격 증명·공개 대상을 이어 쓰지 않습니다. 쓰기·푸시 전에 `pwd`, `git remote -v`, `git status --short`를 확인합니다.

## Gemma 인계 환경

요청한 대상은 **M5 Pro 24GB 통합 메모리에서 MLX 런타임으로 실행하는 Gemma 4 26B**입니다. 이는 사용자가 지정한 환경이며 특정 양자화·컨텍스트의 적합성을 검증한 벤치마크가 아닙니다. 정확한 모델 ID·파일·양자화·도구 호출 형식·런타임 설정은 받는 환경에서 확인해야 합니다.

짧은 대표 작업으로 모델 적재, 남은 메모리, KV 캐시 증가, 생성 속도와 완료 여부를 측정합니다. 근거가 있을 때 컨텍스트를 늘립니다. 코드·도구 출력·마지막 응답 공간을 남기고 현재 작업·제약을 지우기 전에 로그를 줄입니다. 메모리 압력이 높으면 동시 추론을 피합니다. 24GB에서 무조건 가능한 토큰 수를 만들지 말고 실제 설정과 실패를 기록합니다.

이번 DAW 공개는 Gemma를 실행하거나 런타임을 바꾸거나 코딩 세션 성공을 보고하는 작업이 아닙니다. 첫 시험은 T-007 같은 작은 테스트 작업으로, 사람이 검토하고 임시 프로젝트를 사용하며 진행합니다.

## 근거와 효율 측정

작업 ID, 단계·모델·런타임, 확인 가능한 입출력 토큰·비용, 경과 시간, 시도 수, 검토 시간, 검사, 수용 결과와 후속 결함을 기록합니다. 측정하지 않은 값은 `unknown`으로 둡니다.

비교 단위는 재시도·검토를 포함한 **검증되고 수용된 변경 하나의 총비용**입니다. 토큰 비용이 낮아도 결함이 늘면 효율적이라고 단정할 수 없습니다. 비슷한 작업과 같은 기준으로 비교하고 모델 능력·운영 비용·음악 품질을 구분합니다. 측정 전에는 절감률을 주장하지 않습니다.

## 다른 프로젝트에 적용

독립된 `model-tier-handoff` 스킬과 맥락 템플릿을 복사합니다. 새 저장소의 경로·명령·검사·허용 모델에 맞추고 기존 언어·도구·사용자 권한을 유지합니다. 작은 파일럿 결과로 작업 크기를 정합니다. DAW·Node.js·Gemma·유료 다중 에이전트·다른 저장소를 필수로 만들지 않습니다.
